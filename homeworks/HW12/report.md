# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

Датасет: S12-hw-dataset.csv — временной ряд с ежедневной частотой
Прогнозировалось: колонка target на 1 шаг вперёд
Split: temporal split 70% / 15% / 15% (train / val / test) по времени
Подходы: B1 (Naive), B2 (Moving Average), B3 (Ridge), R1 (GRU)
Лучший по validation: R1 (GRU) с MAE = 5.489
Лучший по test: B3 (Ridge) с MAE = 5.414

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: target
- Частота временного ряда: часовая (H)

- Есть ли дополнительные внешние признаки: нет (только производные от target и date)
- Комментарий (2-4 предложения): что важно в данных с точки зрения тренда, сезонности, выбросов, пропусков и сложности прогноза.
Ряд содержит выраженный тренд и недельную сезонность. Пропуски обработаны методом forward/backward fill. Волатильность умеренная, выбросы не критичны. Задача прогноза осложняется нестационарностью ряда.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: с помощью хронологичекого разбиения по времени где 70%  это train, 15% следующих это validation и 15% следующих это test
- Какие доли или интервалы использовались: 70%/ 15%/ 15% 
- Почему `random split` здесь некорректен: модель увидит будущие значения при обучении (утечка), оценка качества будет завышена и нереалистична. Ппрогнозируется будущее на основе прошлого, а с рандомом часть значений из будущего модель уже получит что нельзя. 
### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: lag_1, lag_7, lag_14
- Какие rolling-признаки использовались: rolling_mean_7, rolling_std_7
- Какие календарные признаки использовались: dayofweek, month, dow_sin, dow_cos, month_sin, month_cos
- Как обрабатывались пропуски после построения лагов/rolling: dropna() после построения лагов
- Использовалось ли масштабирование и где именно оно обучалось: StandardScaler, fit только на train

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- B1 (`naive-last`): Прогноз = последнее известное значение (lag_1)
- B2 (`moving-average`): Прогноз = скользящее среднее за 7 дней
- B3 (`ridge-lag-features`): Ridge Regression на лаговых, rolling и календарных признаках
- R1 (`gru-forecast`): GRU с оконным представлением (window_size=28)

Дополнительно:


- Основная метрика выбора лучшей модели: MAE (минимизация `best_val_mae` на validation)
- Дополнительные метрики: RMSE, MAPE (для комплексной оценки)
- `window_size` для `GRU`: 28 (контекст в 4 недели для ежедневных данных)
- Batch size: 64
- Максимальное число эпох: 30
- Optimizer: Adam
- Learning rate: 1e-3 (0.001)
- Как сохранялась лучшая модель: 
  - Сохранялся `state_dict()` модели при достижении нового минимума `val_loss`
  - В конце обучения лучшие веса загружались обратно через `load_state_dict()`
  - Финальная модель сохранена в `artifacts/best_gru.pt`

## 7. Анализ

(8-15 предложений)

Нужно прокомментировать:

Наивный baseline (B1) оказался surprisingly сильным с MAE ~6.3 на test. Это характерно для инерционных рядов, где следующее значение сильно коррелирует с предыдущим. Однако он не учитывает сезонность и тренд.
Moving Average (B2) показал худший результат (MAE ~12.7). Сглаживание по окну 7 дней размывает важные локальные изменения и запаздывает за трендом.
Ridge на признаках (B3) превзошёл простые baseline благодаря использованию множественных лагов (1, 7, 14 дней) и календарных признаков. Модель уловила недельную сезонность и адаптивно взвесила признаки через L2-регуляризацию.
GRU (R1) показала лучший результат на validation, но на test уступила Ridge. Возможные причины: (1) недостаточно данных для глубокой настройки нейросети, (2) переобучение на validation, (3) ряд хорошо описывается линейными зависимостями в лагах.
Тренд и сезонность явно присутствуют в данных. Ridge эффективно использует лаги lag_7 и lag_14 для захвата недельных паттернов. GRU потенциально могла бы лучше уловить долгосрочные зависимости при большем объёме данных.
Утечки данных могли возникнуть при: (1) random split вместо temporal, (2) rolling без shift(1), (3) масштабирование на всём датасете. Все эти риски были устранены.
Выбор по validation принципиален: test используется только один раз для финальной оценки. Если выбирать по test, оценка станет смещённой.
Наиболее показательные ошибки — в точках резкого изменения режима ряда, где все модели запаздывают с адаптацией.

## 8. Итоговый вывод

(3-7 предложений)

Базовый подход для такой задачи: Ridge на лаговых признаках. Прост в реализации, интерпретируем, показывает стабильное качество на test.
Когда достаточно baseline: при ограниченном объёме данных (<10K наблюдений), когда ряд хорошо описывается линейными зависимостями, при необходимости быстрой итерации.
Когда переходить к GRU: при большом объёме данных, наличии сложных нелинейных зависимостей, multi-step прогнозировании, наличии дополнительных внешних признаков.
Главное про валидацию временных рядов: всегда использовать temporal split, никогда не перемешивать данные по времени, масштабировать только на train, выбирать модель по validation, оценивать финально на test один раз.
