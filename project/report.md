- **Название проекта:** RAG-система семантического поиска по Wikipedia на основе Natural Questions
- **Автор:** `Батищев Илья Александрович`

**Краткое описание:** 
Проект представляет собой систему семантического поиска (Retrieval-Augmented Generation) по базе знаний Wikipedia. Система принимает вопрос на естественном языке, находит релевантные фрагменты статей с помощью векторного поиска (FAISS) и возвращает контекст, содержащий ответ. В ходе работы сравнены классический вероятностный подход (BM25) и нейросетевой (Dense Retrieval), выбран оптимальный баланс качества и скорости для production-сценариев.

## 2. Постановка задачи и контекст

### Предметная область и задача
**Задача:** Поиск релевантных текстовых фрагментов в большом корпусе документов (Wikipedia) по запросу на естественном языке.  
**Потенциальный пользователь:** Исследователи, студенты, разработчики, которым нужно быстро найти точную информацию в справочных материалах без ручного перебора статей.  
**Сценарий использования:** Пользователь вводит вопрос (например, *"who was the 16th president of the united states"*), система возвращает топ-5 фрагментов из Wikipedia, где с высокой вероятностью содержится ответ.

### Формулировка задачи в терминах ML/ИИ
- **Входные данные:** Текстовый запрос (вопрос) и корпус документов (чанки Wikipedia).
- **Выход модели:** Упорядоченный список релевантных чанков с оценками семантического сходства.
- **Ограничения/требования:** 
  - Высокий `Recall@5` (релевантный документ должен попадать в топ-5)
  - Низкая латентность поиска (<50мс на запрос)
  - Возможность масштабирования на большие объёмы данных без переобучения

### Целевые метрики качества
| Метрика       | Описание                                                        | Почему выбрана                                                                 |
|---------------|-----------------------------------------------------------------|--------------------------------------------------------------------------------|
| `Recall@5`    | Доля вопросов, где золотой ответ содержится в топ-5 результатах | Ключевая метрика для retrieval: показывает, находит ли система нужный контекст |
| `Latency p95` | 95-й перцентиль времени ответа                                  | Важна для production: пользователь не должен ждать>100мс                       |
| `MRR`         | Средняя обратная позиция первого релевантного результата        | Оценивает качество ранжирования (опционально, для углублённого анализа)        |
|---------------|--------------------------------------------------------------------------------------------------------------------------------------------------|

## 3. Данные

### Источник данных
- **Датасет:** `google-research-datasets/natural_questions` (HuggingFace Datasets)
- **Ссылка:** https://huggingface.co/datasets/google-research-datasets/natural_questions
- **Лицензия:** Открытая (CC BY-SA)
- **Используемый сплит:** `validation` (7 830 вопросов), подвыборка 5 000 для прототипа

### Структура данных
Датасет содержит пары «вопрос — статья Wikipedia»:
- `question`: текст вопроса (строка)
- `document.html`: полный HTML статьи Wikipedia
- `annotations.short_answers`: список коротких ответов (span в тексте)
- `annotations.yes_no_answer`: бинарный ответ (да/нет), если применимо

**Тип данных:** Текстовые (HTML-документы и вопросы), без числовых/категориальных признаков.

### Предобработка и EDA
**Пайплайн обработки:**
1. **Очистка HTML:** Удаление скриптов, стилей, навигации через `BeautifulSoup`
2. **Чанкинг:** Разбиение текста на фрагменты по 300 токенов с перекрытием (overlap=30) для сохранения контекста
3. **Фильтрация:** Отбрасывание чанков короче 50 символов и пустых статей

**Наблюдения из разведочного анализа:**
- Средний размер статьи: ~4 500 слов
- После чанкинга: ~5 000 чанков из 5 000 статей
- ~15% вопросов не имеют `short_answers` (требуют развёрнутого ответа) — исключены из бенчмарка
- Распределение длин вопросов: медиана 8 слов, максимум 32 слова

**Ноутбуки:** Основная логика предобработки реализована в `src/data/chunker.py` и `src/data/loader.py`.

## 4. Модели и подходы

### Базовые модели (Baseline)
**BM25 (Best Matching 25):**
- Классический вероятностный ранжировщик на основе частоты терминов и длины документа
- Реализация: `rank-bm25`
- Параметры: `k1=1.5`, `b=0.75` (стандартные значения)
- Токенизация: простое разбиение по пробелам + lowercasing

**Результат baseline:** Recall@5 = 0.859, Latency p50 = 21.55мс

### Улучшенные модели и эксперименты
**Dense Retrieval (FAISS + Sentence-Transformers):**
- Модель эмбеддингов: `all-MiniLM-L6-v2` (384 измерения)
- Векторный поиск: `faiss.IndexFlatIP` (косинусное сходство)
- Нормализация векторов перед добавлением в индекс
- Батч-эмбеддинг: 64 чанка за раз для ускорения индексации

**Гибридный подход (рассматривался):**
- Комбинация BM25 + Dense с весами α=0.7
- Не включён в финальное сравнение из-за сложности настройки нормализации скоров и незначительного прироста качества на данном объёме данных

### Нейросетевые модели
Использована предобученная модель `sentence-transformers/all-MiniLM-L6-v2`:
- Архитектура: 6-слойный Transformer (MiniLM)
- Размер: ~60MB, эффективно работает на CPU
- Особенности: не дообучалась на наших данных (zero-shot retrieval), используется как feature extractor

### 4.3 Tuning гиперпараметров

Проведена оптимизация ключевых параметров пайплайна на выборке из 200 статей.

**Размер чанка (chunk_size) — оценка по вхождению short_answer:**

| Chunk Size | Recall@5 | Num Chunks | Index Size | Latency p50 |
|------------|----------|------------|------------|-------------|
| 200 tokens | 0.900    | 7 194      | ~110 MB    | 6.5ms       |
| 500 tokens | 0.900    | 2 662      | ~40 MB     | 6.8ms       |
| 300 tokens | 0.880    | 4 568      | ~70 MB     | 6.5ms       |
| 400 tokens | 0.880    | 3 357      | ~50 MB     | 9.4ms       |
|------------|----------|------------|------------|-------------|

**Выбрано:** `chunk_size=300, overlap=30`  
**Обоснование:** Хотя конфигурация 500 токенов показала слегка лучший Recall при меньшем размере индекса, выбран компромиссный вариант 300 токенов по следующим причинам:
1. Разница в Recall (0.900 vs 0.880) находится в пределах статистической погрешности на малой выборке
2. 300 токенов — индустриальный стандарт для RAG-систем, обеспечивающий баланс между точностью контекста и размером индекса
3. Индексы уже построены на этой конфигурации, пересборка нецелесообразна в рамках дедлайна

**BM25 гиперпараметры:**
- Проведён grid search: `k1 ∈ [1.0, 1.2, 1.5, 1.8, 2.0]`, `b ∈ [0.5, 0.65, 0.75, 0.9]`
- Лучшая конфигурация: `k1=1.5, b=0.75` (стандартные значения)
- Отклонения давали прирост <0.5% Recall при потере интерпретируемости

**Результаты экспериментов сохранены в:**
- `experiments/chunk_size_tuning_*.json`
- `experiments/bm25_tuning_*.json`

## 5. Экспериментальный протокол и результаты

### Экспериментальный протокол
**Разбиение данных:**
- **Корпус документов:** 5 000 чанков из `validation` сплита (индексируется целиком)
- **Тестовые запросы:** 200 случайных вопросов из того же сплита с известными `short_answers`
- **Обоснование:** В retrieval-задачах стандартно использовать один сплит для построения индекса и оценки, так как модель эмбеддингов предобучена и не обучается на наших данных (методология BEIR/MS MARCO)

**Процедура оценки:**
1. Для каждого вопроса из бенчмарка выполняется поиск топ-5 чанков
2. Проверяется вхождение нормализованного `short_answer` в объединённый текст топ-5 чанков
3. Замеряется время выполнения (200 запросов для оценки перцентилей)

### Сравнение моделей по метрикам

| Модель / конфигурация         | Описание                              | Recall@5 | Latency p50 (мс) | Latency p95 (мс) | Комментарий                       |
|-------------------------------|---------------------------------------|----------|------------------|------------------|-----------------------------------|
| **BM25**                      | Классический поиск по ключевым словам | 0.859    | 21.550           | 30.490           | Базовый уровень, интерпретируемый |
| **FAISS+MiniLM**              | Векторный поиск + косинусное сходство | 0.970    | 7.820            | 12.690           | Лучший баланс качества и скорости |
|-------------------------------|---------------------------------------|----------|------------------|------------------|-----------------------------------|

### Выбор финальной модели
**Выбрано:** `FAISS + all-MiniLM-L6-v2`

**Обоснование:**
- **Качество:** Recall@5 на 11% выше, чем у BM25 (0.970 vs 0.859)
- **Скорость:** В 2.7 раза быстрее BM25 благодаря оптимизированному C-бэкенду FAISS
- **Простота:** Меньше гиперпараметров для настройки, не требует сложной токенизации
- **Масштабируемость:** FAISS поддерживает миллиарды векторов с HNSW-индексом

**Trade-offs:** 
- FAISS требует больше памяти для хранения эмбеддингов (~70MB vs ~2MB для BM25), но это не критично для текущего объёма данных
- Семантический поиск может находить парафразы, которые не содержат точных ключевых слов (это плюс для user experience)

## 8. Ограничения и дальнейшая работа

Ограничения проекта:
   - Размер корпуса: Прототип на 5 000 чанках, не тестировалось на полном Wikipedia (10M+ статей)
   - Мультиязычность: Модель all-MiniLM-L6-v2 оптимизирована для английского, поддержка русского ограничена
   - Генерация ответов: Endpoint /answer пока возвращает только найденный контекст, без LLM-генерации (требует больше ресурсов)
   - Оценка F1: Метрика F1@5 близка к нулю из-за методологии (сравнение короткого ответа с большим чанком)

Направления развития:
   - Улучшение модели:
      - Fine-tuning MiniLM на NQ с использованием contrastive loss для улучшения retrieval
      - Добавление Cross-Encoder reranking для топ-20 результатов (прирост MRR ~5-10%)
   - Улучшение сервиса:
      - Интеграция локальной LLM (Qwen2.5-1.5B) для генерации ответов в /answer
      - Кэширование частых запросов (Redis/Memcached)
      - Rate limiting и аутентификация API
   - Улучшение данных:
      - Масштабирование на полный train сплит (307K вопросов) с распределённым FAISS
      - Добавление метаданных (дата обновления статьи, популярность) для ранжирования
      - Поддержка мультимодального поиска (таблицы, изображения из Wikipedia)
